# AGENTS.md

## О проекте

Консольный сервис на Python, который подключается к идущему созвону в LiveKit SFU
и в реальном времени транскрибирует речь каждого участника отдельно.

> **Статус:** работает сквозной сценарий на живом SFU: core, pipeline, конфиг и реестр,
> CLI, источники `wav` и `livekit`, VAD `silero` и `energy`, распознаватели `dummy` и
> `faster-whisper` (только final), sinks `stdout` и `http` (протокол — `docs/http-sink.md`),
> saver `filesystem` (запись и переигровка сессий). Не сделано: сам сервер отображения
> (есть только отладочный `scripts/http_sink_server.py`), interim на реальной модели.
> Помеченное «(план)» — целевая архитектура. При расхождении кода и файла — обновлять файл.

LiveKit SFU — **self-hosted** (не LiveKit Cloud), тот же, что у соседнего
проекта `../livekit-bot` (бот создаёт комнаты, имя комнаты — `meetingId`).
Сервис запускается **локально** на машине разработчика с GPU; деплой пока не планируется.
Созвоны — **на английском**: `language: "en"` в конфигах, выбор моделей — под английский.

Основной сценарий:

1. Оператор запускает сервис из консоли с файлом конфигурации и именем комнаты:
   `uv run python -m livekit_transcript --config configs/livekit.json --room <room_name>`.
2. Сервис проверяет конфиг, создаёт компоненты (source, vad, recognizer, sinks, savers)
   и загружает модель распознавания.
3. Источник `livekit` сам генерирует себе токен (`livekit-api`, `AccessToken`) и входит
   в комнату **скрытым участником** (`hidden=True`, только подписка, без публикации медиа).
4. Подписывается на **аудиотрек микрофона каждого участника отдельно** (мультитрек),
   включая тех, кто зайдёт позже. Спикер = `participant.identity` → диаризация не нужна.
5. Каждый трек проходит свой поток VAD → распознавание; сегменты текста с привязкой
   к спикеру и времени уходят во все sink'и и saver'ы.
6. Сервис работает, пока комната жива или до Ctrl+C; при остановке дожидается финальных
   результатов по всем потокам и вызывает `finalize()` у saver'ов.

### Цели

- **Realtime:** текст появляется во время созвона, а не после. Целимся в
  финальный сегмент ≤ ~1.5 с после конца фразы; промежуточные (interim) результаты —
  желательно, контракт их поддерживает с самого начала.
- **Мультитрек:** никогда не микшировать участников в одну дорожку.
- **Заменяемые компоненты:** source, vad, recognizer, sink, saver — каждый выбирается
  в конфиге по `type` и реализует общий интерфейс своего вида. Общий код не знает
  о различиях реализаций (см. «Архитектура»).
- **Локальное распознавание** на своём GPU, без облачных STT.

### Не цели

- **Веб-интерфейс.** В этом сервисе его нет и не будет. Если появится — отдельным
  сервисом, который получает сегменты через отдельный sink (скорее всего — стриминг событий).
- Аудио демонстрации экрана (`SCREEN_SHARE_AUDIO`) — **не распознаётся**, игнорируется.
- Уведомление участников о транскрибации — **пока не делаем**, будет позже.
- Деплой, Docker, автоматический запуск по вебхукам / Agent Dispatch — пока нет.
  Поэтому используется голый `livekit` rtc SDK, а **не** фреймворк `livekit-agents`.

## Архитектура

Пять видов компонентов. У каждого вида — один интерфейс (абстрактный класс в
`core/interfaces.py`, реализации наследуются от него) и несколько реализаций,
выбираемых в конфиге по `type`:

| Вид          | Что делает                                                 | Есть                    | План                    |
|--------------|------------------------------------------------------------|-------------------------|-------------------------|
| `source`     | отдаёт треки спикеров с аудиокадрами                       | `wav`, `livekit`        | —                       |
| `vad`        | превращает поток кадров в события речи                     | `silero`; `energy` (порог громкости, для отладки) | —   |
| `recognizer` | превращает события речи в сегменты текста                  | `faster-whisper`; `dummy` (длительность фразы вместо текста, без GPU) | стриминговые движки |
| `sink`       | получает каждый сегмент по мере появления (realtime-выход) | `stdout`, `http`        | —                       |
| `saver`      | сохраняет сессию целиком: аудио и итоговый транскрипт      | `filesystem`            | —                       |

`energy` и `dummy` — не заглушки для удаления, а отладочные реализации: с ними pipeline
гоняется целиком без моделей и GPU (тесты, проверка источников).

Поток данных для **одного** трека (на каждого спикера — свой экземпляр потоков vad
и recognizer):

```
                 ┌──────────────── кадры ────────────────▶ savers
 source ─ track ─┤
                 └─▶ vad stream ─ события речи ─▶ recognizer stream ─ сегменты ─┬─▶ sinks
                                                                                └─▶ savers
```

**`Pipeline`** (`core/pipeline.py`) — единственное место, где компоненты связываются:
на каждый новый трек создаёт потоки vad и recognizer, раздаёт кадры и сегменты,
закрывает потоки при уходе трека, в конце сессии вызывает `finalize()` у saver'ов.
Pipeline работает только с интерфейсами и не знает конкретных реализаций.

### Контракты компонентов

Общее для всех (`Component`): атрибут класса `Params` (pydantic-модель параметров),
конструктор `__init__(params)`, методы `start()` / `aclose()`. `__init__` — дешёвый,
только проверки (файлы, переменные окружения); тяжёлое (загрузка модели,
подключение) — в `start()`. Pipeline стартует компоненты в порядке sinks → savers →
vad → recognizer → source и закрывает в обратном.

- **Source** — `tracks()`: асинхронный итератор `SpeakerTrack`. Каждый трек содержит
  `Speaker` (`id`, `name`) и асинхронный итератор `AudioFrame`. Источник **обязан**
  приводить аудио к единому формату: PCM int16, **16 кГц, моно**, с временем начала
  кадра (UTC). Конец итерации треков = конец сессии. `stop()` — просьба корректно
  завершиться: треки и их кадры скоро заканчиваются. `session_name` — имя сессии для saver'ов.
- **VAD** — `process(frames)`: преобразует кадры **одного** трека в события
  `SpeechStart` / `SpeechFrames` / `SpeechEnd` (асинхронный генератор, вызывается
  на каждый трек, состояние вызовов не общее). Каждый `SpeechStart` закрывается
  `SpeechEnd`, в том числе при конце кадров. VAD только размечает речь.
- **Recognizer** — `transcribe(speaker, events)`: преобразует события речи одного
  трека в `TranscriptSegment` (interim/final).
  - Нарезающий движок (faster-whisper) копит кадры фразы и распознаёт её на `SpeechEnd`.
  - Стриминговый движок распознаёт по мере поступления `SpeechFrames` и выдаёт
    interim-сегменты, а `SpeechEnd` использует как сигнал финализировать фразу.
  - Модель загружается **один раз** в `start()` и разделяется всеми треками;
    инференс — вне event loop (`asyncio.to_thread` / поток-воркер с очередью к GPU).
- **Sink** — `on_session_start(session)`, `on_track_start(speaker)`, `on_segment(segment)`
  на каждый сегмент (interim и final), `on_track_end(speaker)`, `on_session_end()`;
  обязателен только `on_segment`. Медленный sink не тормозит распознавание: pipeline
  кормит каждый sink из своей очереди (одной на все его события — порядок сохраняется)
  и предупреждает в лог, если очередь разрослась.
- `SessionInfo.id` — UUID на каждый запуск: одну комнату (`name`) можно транскрибировать
  несколько раз.
- **Saver** — получает события сессии по ходу: `on_session_start`, `on_track_start`,
  `on_frame`, `on_segment` (**только финальные**), `on_track_end`, а в конце —
  `finalize()` (вызывается всегда, в том числе при ошибке). Аудио **пишется на диск
  инкрементально**, а не копится в памяти до конца созвона.

Ошибки: исключение в обработке одного трека логируется и не роняет сессию;
исключения sink'ов и saver'ов логируются и не роняют pipeline.

Правила слоёв (проверять при ревью):

- Пакеты реализаций (`sources/`, `vad/`, `recognizers/`, `sinks/`, `savers/`)
  импортируют только `core/` и не импортируют друг друга.
- `core/` не зависит ни от каких внешних SDK и ни от одной реализации.
- Тяжёлые и специфичные зависимости живут только в своём модуле: `livekit` — в
  `sources/livekit.py`, `faster_whisper` — в `recognizers/faster_whisper.py` и т. д.
- `vad/` не использует `livekit-plugins-silero` (тянет `livekit-agents`), пакет
  `silero-vad` (тянет PyTorch) и копию Silero из faster-whisper (другой, пакетный
  интерфейс модели + зависимость от распознавателя). Модель лежит в `vad/silero_vad.onnx`.

### Конфигурация сессии (JSON) и реестр

Состав pipeline задаётся JSON-файлом. У каждого компонента — `type` (какая реализация)
и `params` (её параметры). `sinks` и `savers` — списки: можно включить несколько сразу
или ни одного.

```json
{
  "source": {
    "type": "livekit",
    "params": { "room": "my-room" }
  },
  "vad": {
    "type": "silero",
    "params": { "threshold": 0.5, "min_silence_ms": 500 }
  },
  "recognizer": {
    "type": "faster-whisper",
    "params": { "model": "large-v3-turbo", "device": "cuda",
                "compute_type": "float16", "language": "en" }
  },
  "sinks": [
    { "type": "stdout", "params": { "format": "jsonl" } }
  ],
  "savers": [
    { "type": "filesystem", "params": { "dir": "./sessions" } }
  ]
}
```

Источник из WAV-файлов — по файлу на спикера (PCM 16 бит, 16 кГц, моно; другое —
ошибка конфига с командой ffmpeg для конвертации); `realtime: true` отдаёт кадры
в темпе реального времени (для проверки realtime-поведения без SFU); `offset_ms` —
когда файл начинается относительно старта сессии (спикер зашёл позже):

```json
"source": {
  "type": "wav",
  "params": {
    "files": [
      { "path": "samples/alice.wav", "speaker_id": "alice", "speaker_name": "Алиса" },
      { "path": "samples/bob.wav",   "speaker_id": "bob",   "speaker_name": "Боб",
        "offset_ms": 0 }
    ],
    "realtime": true
  }
}
```

`--source <файл>` в CLI заменяет секцию `source` конфига содержимым файла (обычно
`source.json` сохранённой сессии): так запись переигрывается с любыми настройками
VAD/распознавателя из основного конфига.

Как это устроено в коде:

- У каждой реализации есть pydantic-модель параметров (`Params`, наследник
  `ComponentParams`). Все компоненты создаются **до старта любого из них**:
  опечатка в параметре — понятная ошибка за секунду, а не падение после загрузки
  модели на GPU. Неизвестные поля в `params` — ошибка.
- Ошибки конфига и окружения — `ConfigError`: CLI печатает сообщение без traceback
  и выходит с кодом 2.
- `registry.py` сопоставляет `(вид, type)` → реализация. Модули реализаций
  импортируются **лениво** — только выбранные в конфиге (чтобы, например, без
  установленного CUDA можно было запустить `wav` + другой recognizer).
- Добавить реализацию = новый модуль в пакете своего вида + одна строка в реестре.
  Общий код при этом не меняется.
- Ключи JSON — `snake_case`. Секреты в JSON **не кладутся** — только в `.env`.

### Формат сегмента

`TranscriptSegment`, как его выводит `stdout`-sink (одна строка JSONL на сегмент):

```json
{"speaker_id": "alice-123", "speaker_name": "Алиса", "segment_id": "alice-123:17",
 "is_final": true, "start": "2026-10-31T10:15:02.120Z", "end": "2026-10-31T10:15:04.870Z",
 "text": "Привет, слышно меня?"}
```

- `segment_id` стабилен для одной фразы: interim-сегменты с тем же id заменяют
  предыдущие, финальный — последний для этого id. Потребитель обновляет реплику на месте.
- `segment_id` уникален в сессии: номер фразы сквозной на спикера в пределах
  распознавателя, а не трека — переподключившийся участник не повторит `alice:1`.
- Время — абсолютное UTC, присвоенное источником; по нему упорядочиваются реплики
  разных спикеров.
- stdout принадлежит `stdout`-sink'у. Служебные логи (`logging`) — только в stderr.

### Остановка

Первый Ctrl+C — корректная остановка: `pipeline.stop()` → `source.stop()`, треки
заканчиваются, недоговорённые фразы закрываются VAD и распознаются, saver'ы
финализируются, код выхода 0. Второй Ctrl+C — немедленный выход (код 130).

### Источник `livekit` — поведение

- Перед входом проверяет через Server API (`ListRooms`), что комната есть: вход в
  несуществующую комнату либо создал бы пустую, либо (на нашем SFU автосоздание
  выключено, комнаты создаёт бот) упал бы с 404. Нет комнаты / SFU недоступен /
  ключи не подходят — `ConfigError`, код выхода 2.
- Identity — `params.identity` + случайный суффикс (`transcriber-1a2b3c`): участник
  с тем же identity выбил бы предыдущего (два транскрибатора в одной комнате).
- Подписка только на аудио с источником `MICROPHONE`; `SCREEN_SHARE_AUDIO` игнорируется.
  Агенты (`ParticipantKind.AGENT`) игнорируются; скрытых участников SFU и так не показывает.
- Участники, бывшие в комнате до нас и зашедшие позже, подхватываются одинаково
  (`track_subscribed`, `auto_subscribe=True`). `track_unsubscribed` (вышел, снял трек) —
  `SpeakerTrack` закрывается, распознаватель дожимает последнюю фразу.
- Mute — просто нет кадров, трек не закрывается.
- Переподключение участника с тем же `identity` — новый трек того же `Speaker`.
- Комната удалена / нас отключили — конец сессии, код выхода 0.
- Кадры: `rtc.AudioStream(track, sample_rate=16000, num_channels=1)` (ресемплинг в SDK).
  Время кадра — момент получения минус длительность кадра. Свой `_TrackFeed` с
  очередью на трек: трек закрываем своим сигналом, не дожидаясь end-of-stream от SDK
  (`AudioStream.aclose()` ждёт его и может зависнуть).
- Проверено на нашем SFU (`LIVEKIT_URL` из `.env`) через `scripts/publish_wav.py`: задержка
  final 0.6–1.2 с после конца фразы.

### `scripts/publish_wav.py` — тестовые участники

Отладочный скрипт: создаёт комнату через API (если её нет), заводит по участнику на
WAV-файл и проигрывает файлы как их микрофоны в реальном времени. `--delay` — пауза
перед речью, чтобы успеть запустить транскрибатор; `--delete-room` — удалить комнату
в конце (транскрибатор увидит `ROOM_DELETED` и завершит сессию).

```bash
uv run python scripts/publish_wav.py --room test-1 --delay 15 --delete-room \
    samples/alice.wav:alice:Алиса samples/bob.wav:bob:Боб
uv run python -m livekit_transcript --config configs/livekit.json --room test-1  # в другом терминале
```

### Saver `filesystem` — запись и переигровка сессий

Зачем: баг на живом созвоне → та же сессия локально через источник `wav`, с любыми
настройками. Включается конфигом (`configs/livekit-record.json`), по умолчанию запись
не ведётся — это запись звонка.

Каталог сессии `<dir>/<session>-<локальное время старта>/` (`-2`, `-3` при совпадении):

- `<speaker_id>.wav` — сырое аудио спикера (до VAD) с его первого кадра, дописывается
  по ходу созвона; заголовок WAV обновляется раз в секунду аудио — после падения
  процесса файл читаем. Небезопасные для имени файла символы id → `_`.
- `segments.jsonl` — финальные сегменты по мере появления (как `stdout` jsonl).
- `source.json` — секция `source` для источника `wav`: абсолютные пути, `speaker_name`,
  `offset_ms` первого кадра спикера от старта сессии, `realtime: false`. Пишется при
  появлении каждого нового спикера (переживает падение) и в `finalize()`.
- `transcript.txt` — в `finalize()`: реплики всех спикеров по времени,
  `[чч:мм:сс] Имя: текст` (пустые final пропускаются).

Время внутри файла:
- Переподключившийся спикер дописывается в тот же файл.
- Разрыв между кадрами ≥ `min_gap_ms` (500) заполняется тишиной по меткам времени —
  файл остаётся на шкале сессии. Меньшие разрывы не заполняются: метки LiveKit — время
  прихода кадра, их дрожание при заполнении сдвигало бы файл вперёд реального времени.
- На практике LiveKit присылает кадры непрерывно с момента подписки, тишину тоже:
  `offset_ms` ≈ моменту входа участника, дыр почти нет.

Проверено на SFU: записанная через `publish_wav.py` сессия, переигранная через
`--source`, дала те же 14 реплик слово в слово (включая ошибку распознавания).
~1.9 МБ на минуту на спикера.

### VAD `silero` и `energy`

Оба решают только «речь ли этот кусок»; превращение решений в фразы (`SpeechStart` /
`SpeechFrames` / `SpeechEnd`, `pre_roll_ms`, `min_silence_ms`) — общий
`vad/segmenter.py:PhraseSegmenter`.

- `silero` — нейросетевой Silero VAD 6.2.3, ONNX через `onnxruntime` на CPU, без PyTorch.
  Модель `vad/silero_vad.onnx` взята без изменений из wheel `silero-vad` 6.2.3 с PyPI
  (sha256 `1a153a22…88e3`), лицензия MIT — `vad/silero_vad.LICENSE`; входит в wheel пакета.
  - Входящие кадры (10–20 мс) перерезаются в окна модели по 512 сэмплов (32 мс) +
    64 сэмпла контекста от предыдущего окна; состояние модели — своё на трек,
    `InferenceSession` — одна на процесс.
  - Гистерезис: фраза начинается при вероятности ≥ `threshold` (0.5), внутри фразы
    тишина — < `neg_threshold` (по умолчанию `threshold − 0.15`, как в `VADIterator` Silero).
  - Хвост короче окна не классифицируется: внутри фразы он дописывается к ней.
  - ~0.17 мс CPU на окно (0.19 с на 36 с аудио) — считается прямо в event loop,
    перескок в поток дороже самого инференса.
  - На `samples/alice.wav` с шумом −35 dBFS и щелчками: `silero` — те же 8 фраз, что на
    чистой записи; `energy` — одна «фраза» на весь файл. Тон и белый шум `silero` речью
    не считает (есть тест).
- `energy` — порог громкости, без модели: для отладки и тестов pipeline.

### Распознаватель `faster-whisper`

- Копит кадры фразы и распознаёт её целиком на `SpeechEnd` → final-сегмент.
  `interim_every_ms` — перераспознавание незаконченной фразы для interim-сегментов
  (реализовано, по умолчанию выключено, на реальном созвоне ещё не проверялось).
- Модель грузится в `start()` и сразу прогревается (первый инференс в разы медленнее).
  Инференс — в одном потоке-воркере (`ThreadPoolExecutor(max_workers=1)`): GPU
  обрабатывает одну фразу за раз, треки встают в очередь.
- Против галлюцинаций Whisper: фразы короче `min_phrase_ms` не распознаются,
  `condition_on_previous_text=False`, `no_speech_threshold`. Пустой текст — сегмента нет,
  но если по фразе уже были interim-сегменты, отдаётся пустой final, чтобы их закрыть.
- На вход модели — numpy float32, не файл: декодирование файлов в faster-whisper 1.2.1
  несовместимо с `av` 19.
- Замер на `samples/` (RTX 4070, `large-v3-turbo` float16, realtime): текст приходит
  через 0.6–1.0 с после конца фразы, из них ~0.5 с — `min_silence_ms` VAD.

**CUDA на Windows.** CTranslate2 нужны CUDA 12 cuBLAS и cuDNN 9 — ставятся pip-пакетами
`nvidia-cublas-cu12`, `nvidia-cudnn-cu12` (CUDA Toolkit не нужен). Их DLL не на пути поиска,
поэтому `_add_cuda_dll_dirs()` добавляет `site-packages/nvidia/*/bin` перед загрузкой модели.
`nvidia-cublas-cu12` ограничен `<12.9.3`: у 12.9.3.13 нет wheel под Windows.

Окончательный выбор движка открыт; язык — английский. Другие кандидаты:
**distil-large-v3.5** (английский дистиллят Whisper, быстрее turbo — тот же recognizer,
другой `model`), **NVIDIA Parakeet TDT** (английский, высокая точность и скорость,
нужен новый recognizer), **sherpa-onnx** streaming Zipformer (CPU, настоящий стриминг).

## Переменные окружения

Только секреты и адреса (файл `.env` локально). Всё остальное — в JSON-конфиге.

| Переменная              | Описание                                                       |
|-------------------------|----------------------------------------------------------------|
| `LIVEKIT_URL`           | адрес SFU в любой схеме: `https://host/livekit`, `wss://host`, `http://localhost:7880`. Из него выводятся оба адреса: http(s) — Server API, ws(s) — подключение к комнате |
| `LIVEKIT_API_KEY`       | API key LiveKit                                                |
| `LIVEKIT_API_SECRET`    | API secret LiveKit                                             |
| `HTTP_SINK_URL`         | куда sink `http` шлёт POST; `https://`, `http://` — только на localhost или с `allow_insecure` |
| `HTTP_SINK_TOKEN`       | общий с сервером отображения токен, уходит как `Authorization: Bearer`; случайный (`secrets.token_urlsafe(32)`) |

`--room` в CLI переопределяет `source.params.room` (только для источника `livekit`).

## Команды

```bash
uv sync                                                                   # зависимости
uv run python -m livekit_transcript --config configs/livekit.json --room <room_name>
uv run python -m livekit_transcript --config configs/livekit-record.json --room <room_name>  # + запись в sessions/
uv run python -m livekit_transcript --config configs/livekit.json --source sessions/<сессия>/source.json  # переиграть
uv run python -m livekit_transcript --config configs/wav.json            # без SFU, нужны samples/*.wav
uv run pytest                                                             # тесты (без GPU)
uv run pytest -m gpu                                                      # тесты на GPU и samples/
uv run ruff check . --fix                                                 # линтер
uv run ruff format .                                                      # форматирование
```

Перед завершением задачи агент должен прогнать `ruff check`, `ruff format` и `pytest`.

## Соглашения по коду

- Весь I/O — асинхронный. Тяжёлые/блокирующие вызовы (инференс, загрузка модели,
  запись больших файлов) — только вне event loop.
- Аннотации типов обязательны для публичных функций.
- Общий код (pipeline, CLI) обращается к компонентам **только через интерфейсы**
  из `core/interfaces.py`. Никаких `isinstance` / `if type == "..."` по реализациям
  вне `registry.py`.
- Каждая фоновая задача (`asyncio.create_task`) должна иметь владельца, который её
  отменяет и дожидается при остановке; исключения в задачах не должны теряться молча.
- Логирование — стандартный `logging` в stderr, без `print`. stdout принадлежит sink'у.
- Тесты pipeline — на источнике `wav` (WAV генерируются в тесте: тон/тишина),
  `energy` + `dummy` и фейковых sink/saver из `tests/helpers.py`, без живого SFU.
  Распознаватели тестируются на фейковой модели (подмена `_load`). Тесты, требующие
  GPU, — маркер `gpu` (исключён по умолчанию в `addopts`); требующие SFU — свой маркер.
- Комментарии в коде — на английском; сообщения пользователю (логи, ошибки) — на русском.

## Безопасность и приватность

- Никогда не коммитить `.env`, токены и секреты. В репозитории только `.env.example`.
- Не логировать `LIVEKIT_API_SECRET` и сгенерированный токен.
- `LIVEKIT_API_SECRET` текущего SFU — 30 байт, PyJWT предупреждает
  (`InsecureKeyLengthWarning`, нужно ≥ 32 для HS256). Не глушить: лечится
  заменой секрета на SFU (общий с `livekit-bot`).
- Токен сервиса — минимальные права: `room_join` в одну комнату, `can_subscribe=True`,
  `can_publish=False`, `hidden=True`, короткий TTL.
- Транскрипты и аудио — персональные данные: текст речи не писать в логи выше DEBUG,
  каталог сессий (`sessions/`) — в `.gitignore`.
- `HTTP_SINK_TOKEN` идёт в заголовке открытым текстом — защищает его только TLS, поэтому
  sink `http` отказывается слать на `http://` не-localhost без `allow_insecure: true`.
  Дополнительно шифровать токен бессмысленно; следующий уровень, если понадобится, —
  HMAC-подпись тела с меткой времени (защита от подмены и повтора).
